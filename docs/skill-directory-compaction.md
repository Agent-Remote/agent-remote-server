# Skill 当前目录整理

本文件记录已实现的内部目录整理服务及其验证边界；公开 prune 仍待接入。
基线契约是根设计 §4.5、§8.2 与 `skill-retention.md`。现有内部退役故意拒绝当前目录
成员和保留 backing 依赖，不能由调用方删除成员记录或改写审计摘要来绕过。

## 选择与保护

整理从已授权账户、明确 item/完整目录范围和固定用户锁视图出发。历史分支是否当前，
必须复用保活分析中的规则解析、安装纪元和 pin 判定，不能只比较目录中的名字。
同一目录名可曾属于不同 revision/epoch；选择必须保留稳定来源、分支与 checkpoint 身份。
当前解析分支即使停用仍受保护。活动本地初始、snapshot、收尾、冲突、接管和仍有效的
精确增量基线都不能通过“整理”被改写成别的输入。

只有明确选择且达到等待资格的历史成员可以从当前物化视图移除。root 级辅助内容不是
无主垃圾，未被明确授权的当前辅助数据要保留。选择旧版成员不授权覆盖同名新版的 head，
也不授权修改默认版本、启用状态、pin、来源身份或安装纪元。

## 内容等价和依赖

需要检查两类完整树：当前目录树，以及仍受保护单项 head 实际引用的完整 backing 树。
它们可能不同；只整理目录树不能解除单项 head 对旧树的引用。必须分别分析每份树的
顶层根、直接/间接相对链接及受管运行时依赖。可复用 `directory_merge_units` 的真实链接
解析，不能用字符串前缀判断依赖，更不能以关闭 manifest 校验的方式拆开关联单元。

对于每个保留的单项视图，整理前后必须证明其导出依赖单元中所有条目的路径、类型、字节
摘要、大小、模式和链接目标完全一致，包括空目录、根目录模式、显式删除和无效 skill
格式。候选历史根若仍与该单元相连，应作为保留依赖列入预览，不得为了回收而改写链接。

如果需要给当前分支建立内容等价的新 checkpoint，应保留 state epoch，明确记录旧 head
与新 backing 的关系，用新完整树摘要和新身份；不能就地改写旧 checkpoint 或它的
content_digest。不能改写精确增量基线、活动输入或其他历史视图的身份来制造可回收性。
原有 snapshot/publication 的旧输入继续由自己的保留引用负责。

## 原子发布与等待时钟

预览必须固定目录 head/epoch、全部受影响分支 head/epoch/expired、库代数、准确成员
身份、各树摘要，以及待移除根和无法移除的依赖。只读预览不创建新树、checkpoint、
上传或保留时钟。提交在同一用户锁与保存点内重新计算并比较完整计划；任一变化应重新
预览，不能把用户确认解释为对后来新内容的删除授权。

新目录、必要的等价单项视图、成员集合和 head 交换须一次提交；失败全部回滚。旧目录
成员与 backing 身份作为不可变审计保留。发布成功才重新计算保护和真实释放时间；
不从旧 checkpoint 的创建时间推断整理后的保留截止。

普通 prune 不得自动把刚解除保护的旧目录或旧单项视图当作已等待 30/90 天的历史。
保守实现可以先整理、保留这些新近释放的完整历史，等其真正到期再退役；预览必须明确
当前实际能释放的引用和仍在等待的内容。显式 all-unreferenced 才可以越过等待，且仍须
经过整理后的完整硬保护、历史依赖与账户范围校验。此语义应在公开接口实现前纳入
CLI 预览，不能显示只减去候选文件大小算出的虚假回收空间。

## 配额与验收边界

新视图可能共享现有对象，也可能暂时增加树/引用元数据；空间结算应按提交后每个分类
真实保留的唯一对象计算。另一个状态/包引用或有效上传租约仍保留的物理文件不得删除。
树/对象引用释放、deleting 标记、持久化删除任务、复用准入和重试属于后续 GC 事务。
目录整理单独通过不证明上述工作完成。

至少需要覆盖：仅旧成员可移除、停用当前项保留、同名不同版本与纪元、不同 backing 树、
跨根链式链接、外部受管依赖、空根和无效格式、全账户与单项范围、精确增量基线不变、
活动流程阻断、头部 CAS 竞争、提交/回滚、默认等待与显式提前、共享对象零实际回收量、
以及旧目录成员/回执仍可查但退役内容不能导出。

## 本轮内部服务契约

内部 preview 接受同账户不同的 item checkpoint 身份，受完整保留索引的一百万身份
安全预算约束，不用名称代替所有权；整份选择不按独立 1000 项批次提交。
每个选择都必须未受硬保护、内容 retained 且满足自身普通/归档期限，或显式提前等待。
服务只从当前目录及受保护分支 head 的明确 backing 目录中，移除恰好对应这些身份的
成员根；未选择成员和根级辅助数据始终保留。链接连通单元无法完整移除时返回阻断成员。
缺少 backing 证据的旧 head 保留原样并在计划中标注，不按名称推断其其他根归属。

计划固定当前目录、库代数、所有受保护 head、原成员和树，以及规范化的结果/阻断清单。
实际发布重新构建并要求计划相等。目录内容变化后，成员替换可能继续影响其他当前/backing
目录；按有限闭包创建必要的新目录和等价 head，避免留下仍指向旧 head 的当前物化成员。
新 checkpoint 不冒充 session 产物，保留 parent 和实际创建纪元；state/directory epoch 不
因等价整理推进。所有新内容只引用已有完整对象，验证和配额准入与通常内容服务一致。

基础整理提供内部 preview/apply，apply 不承诺独立的持久化幂等回执；未来公开 prune 必须
把它放进原请求/回执事务后才能暴露。预览无上传/计量/时钟写入，发布由调用方决定提交。
整理不退役任何旧 checkpoint、不结算或声称释放字节，也不自动改变分支 expired。
发布后旧历史的真实截止与内容依赖由既有保留事务处理。组合入口
`reclamation_preview/apply_reclamation` 另行接入完整历史退役与实际 GC，
见 `skill-prune-projection.md`；基础整理单独执行仍没有删除语义。

资源边界：受保护分支 head 与完整目录的身份合计最多 1,000,000 个，
累计清单条目最多 1,000,000 个；
达到上限整体拒绝，不返回可误用的部分计划。此限制不代表容量或性能验收。


## 当前实现与证据

`services/skills/compaction/` 分离固定计划、完整分析和原子发布。preview 使用现有一致读锁，
apply 使用 `retention_mutation` 保存点，重建完整计划后才登记新树、目录和单项 checkpoint。
内容变化会通过当前成员和受保护 head 的 backing 关系计算有限更新闭包；因此即使当前
目录字节未变，其成员指向需要更新时也会生成新目录，不就地编辑旧成员。受保护 head
在同一树上的实际 subtree_prefix 独立阻止移除，避免旧成员身份与新视图别名不一致时误删。

两份不同 backing 树分别整理。当前目录中同名但未选择的 checkpoint 内容不会因另一个
历史成员被选中而删除。新单项导出单元与原单元的路径、摘要、模式、空目录和链接完全
一致；无效 skill 文件仍原样保留。无法证明 backing 的旧 head 不更换，其原树继续引用。
已成功迁移的精确基线和快照成员不改写；基线仍保活旧 checkpoint，后续真实增量迁移通过。

预览检查实际完整字节、单项/完整目录上限及聚合状态配额。缺失文件和收紧的配额在任何
内容登记前拒绝。无变化计划不创建上传/树/checkpoint；发布失败及外层回滚撤销全部新
引用与时钟。等价 head 和目录释放旧保护时才启动旧身份的历史时钟；整理本身没有退役
或释放配额，不能报告物理回收量。

SQLite 首批 13 例及补充 4 例通过；两个真实行锁竞争用例仅在 PostgreSQL 运行。首轮
PostgreSQL 17 合并引用/时钟/退役/整理 63 例通过，结构由 Alembic 初始化至 0041。
包含补充边界的最终 PostgreSQL **67 例通过**；临时数据库容器与匿名卷已删除。
最终完整 Server 门禁 **1160 passed、24 skipped、80.90% coverage**；Ruff、
Mypy（411 文件）、中文注释和空白检查全部通过。日志
`/tmp/skill-directory-compaction-server-quality-verified.log`。两个新增跳过项是已在
PostgreSQL 通过的独立连接整理/pin 竞争。
日志 `/tmp/skill-directory-compaction-focused.log`、`/tmp/skill-compaction-extra-boundaries.log`、
`/tmp/skill-directory-compaction-postgres.log`、`/tmp/skill-directory-compaction-postgres-verified.log`、
`/tmp/skill-directory-compaction-postgres-migration.log`。增量迁移后的目录也经补充断言确认
不会重新引入已移除的 learning 根：`/tmp/skill-compaction-baselines-verified.log`。

仍需公开 prune 的范围解析、完整失去恢复能力清单、一次确认、持久化原请求/回执、
整理后历史退役、树/对象引用释放、精确额度结算、持久化删除与 deleting 复用准入。
此内部 apply 不是可直接暴露到 HTTP 的幂等命令。schema head 仍为 0041；没有启用公开
prune、接管 dispatch 或 runtime capability。

公开 prune 接入的原请求、摘要式确认、整理后保护投影和删除事务约束已记录在
`skill-state-prune.md`。尤其不能把内部含完整树的计划直接塞入 CLI 的有界原请求日志，
或把分批内部调用等同于公开账户范围的完整原子计划。
