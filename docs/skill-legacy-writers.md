# 接管期间的旧写入者准入

首次接管必须等待已有 legacy 会话与绑定进程退出，同时阻止新任务启动另一名旧目录写入者。
目前绑定和后端迁移服务在任何账户、profile、task、audit 变更前取得用户内容锁，再刷新
账户目录模式。migrating/managed_v1 均返回 `MIGRATION_PENDING`（409），功能开关关闭也
不会释放已接管的目录。legacy 和无目录记录账户保留原有行为。

这两个入口目前都操作旧账户目录，不能凭节点广告或客户端传入 snapshot 字段成为受管流程。
之后开放 managed binding/backend migration 时，必须实现专门的快照及状态保留适配，不能
简单移除此检查。现有受管会话准入仍使用精确快照事务；读取、停止与退出状态处理不受影响。

Node Helper 在同一串行执行边界检查持久化账户围栏，拒绝排队的 Native/Docker 启动、绑定及
后端迁移。Docker 的账户路径由 Helper 从已检查身份构建，忽略任务的 account_remote_path；
已有账户路径祖先和发现根以 no-follow 目录句柄预检。Native 内部 launch 入口再次拒绝旧
spec；声明 snapshot ID 仍须通过已有私有收据与挂载绑定验证，不能直接获得启动权限。

围栏准入检查不会发出 stop/kill，也不证明旧进程已退出。正常停止入口保持可用，成功旧任务
的缓存重放只返回结果，不重新启动进程。完整接管仍需清点旧会话与绑定资源、排空导入、核实
整个进程组退出、稳定捕获原目录并完成单次权威提交。任务取消、租约到期或不在心跳列表中
都不足以证明静止；原目录不得被作为第二份可变主库继续写入。
